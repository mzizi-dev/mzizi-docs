<Note>
  This section documents Mzizi's **components**: the registry and design system that
  support the language, served through [`api.mzizi.dev`](/platform/api-gateway) and browsable at
  [mzizi.dev/components](https://mzizi.dev/components). It is not documentation for the
  language itself; [the ecosystem page](/ecosystem) draws the line. Rust components
  ([Mzizi Roots](/roots/overview)) lead. The React components are **the React build**:
  they keep working, but they are deprioritised.
</Note>

The Mzizi registry is the set of components, tokens and architecture that Mzizi applications
are built from: built to support the language as its UI layer. It also supplies the
ground truth for the language benchmark's UI tasks, as one of its jobs. It lives in
[`mzizi-dev/mzizi-registry`](https://github.com/mzizi-dev/mzizi-registry) as files, and it is
served over the public API at [`api.mzizi.dev`](/platform/api-gateway) and the
[MCP server](/toolchain/mcp).

## Two builds of the same components

| Build               | What it is                                                                               | State                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **Rust**            | Dioxus components in the `mzizi-rs/` crates, growing into [Mzizi Roots](/roots/overview) | Leads. `cargo add mzizi-roots`; source and its crate at `/v1/rs/{name}` |
| **The React build** | TypeScript and React (`.tsx`) components, shadcn-compatible                              | Works and installs today. Deprioritised                                 |

Every primitive with a Rust sibling has a contract test in the registry asserting that the
`.tsx` and the `.rs` agree on variants, `data-slot` names and classes. Where both exist,
present the Rust one first.

The React build installs with the shadcn CLI, one command per component:

```bash
npx shadcn@latest add https://api.mzizi.dev/v1/ui/button
```

That fetches the component JSON, resolves its dependencies, and writes the source into your
project as a file you own. See [consuming the registry](/registry/consuming).

| `registry:block` | 105     | composed page sections |
| `registry:lib`   | 47      | `lib/`                 |
| `registry:hook`  | 3       | `hooks/`               |
| `registry:base`  | 1       | the base layer         |
| `registry:theme` | 1       | the theme              |
| **Total**        | **577** |                        |

Counts move. `GET /v1/ui` is the live answer; prefer it to a number written down anywhere,
including here.

## Where the source of truth is

`registry.json` at the root of the registry repository is the manifest, and the component
source sits beside it on disk under `components/registry/n<number>-<name>/`. The API reads
both, at build time, from a pinned registry commit.

<Warning>
  **There is no database behind the registry.** Component source is not stored in a
  database, and writing a component with SQL is not a supported path. It was, and the
  practice was retired; then the database itself was removed from the registry on
  29 September 2026. The only database in Mzizi is the console's. See
  [where data lives](/platform/data).
</Warning>

## Naming

Naming is a deliberate mix. Framework-standard primitives keep their plain names: `button`,
`dialog`, `card`. Many of Mzizi's own branded composites carry the `mzizi-` prefix. Components that used to be named `nyuchi-*` are now
`mzizi-*`, and the old names redirect: `GET /v1/ui/nyuchi-sidebar` answers `308` to
`/v1/ui/mzizi-sidebar`.
