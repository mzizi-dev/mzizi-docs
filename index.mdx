<Note>
  **Read [Status](/status) first.** Mzizi is a Phase 0 research prototype. The compiler
  front end exists and is tested: a lexer, a recovering parser, a name and type resolver, an
  agent diagnostic protocol, contract evaluation, a content-addressed IR and nine primitives
  written in Mzizi. Nothing lowers to Rust yet and nothing renders. Two small pilots of the
  benchmark ran on 2026-09-27, and **neither showed an advantage** ([results](/pilots)). The
  run that tests the kill criterion has not happened.
</Note>

_Mzizi_ means **root**. Mzizi is a language, and these docs lead with
it. Everything else Mzizi makes (the compiler toolchain, the MCP server, the CLI, the API
and the components) exists to support the language and make it stronger.

## The claim worth defending

Every web framework was designed assuming a human is typing, reading docs and holding
context in their head. The charter's bet is that this is the wrong assumption for where
development is going:

> Mzizi's single sharp edge: **a Rust framework whose syntax, type system, and compiler
> feedback loop are designed for machine authorship, not just human ergonomics.**

Then a correction that matters more than the original claim. RFC-0001 was written by a
frontier model optimising for its own experience, and [RFC-0002](/rfcs) withdrew that
target:

> **The design target is small models.** A 7B open-weight model running locally, not a
> frontier model with a million-token context. Frontier capability is improving on its own;
> the language cannot help there and does not need to.

That inversion is why token efficiency is a first-order goal, why `end component button`
echoes the name back, and why the grammar is small and closed rather than familiar and open.
It is also why the second pilot matters: it tested that design target, and the ~7B model
did worse in Mzizi than in Dioxus.

## Where Mzizi is heading

<Note>
  **Direction, not shipped.** These are the owner's stated goals as of 29 September 2026.
  The RFCs that turn them into designs are being written in
  [`design/`](https://github.com/mzizi-dev/mzizi/tree/main/design). Read
  [the roadmap](/roadmap) for how they relate to the phases.
</Note>

- **The whole stack, not only the UI.** Mzizi is meant to build the backend as well as the
  interface. Mzizi's own backend infrastructure is meant to be built with it.
- **Two frontend shapes.** Astro with Mzizi UI ([Mzizi Roots](/roots/overview)) underneath,
  or pure Rust end to end.
- **Contracts everywhere.** Everything built carries a contract: components, language
  functions and backend handlers. Today only component contracts exist.
- **A wider benchmark.** The benchmark will extend to TypeScript and React, Python, Go and
  C++, on frontend and backend tasks. Today it compares Mzizi with Dioxus and Leptos on UI
  components.
- **A higher bar.** The kill criterion is now Mzizi against the best existing language for
  each kind of task, aiming to rank with the top languages. It has not been measured.
- **Every result published.** Every benchmark run lands in
  [`benchmarks/results/`](https://github.com/mzizi-dev/mzizi/tree/main/benchmarks/results),
  whichever way it falls.

## What Mzizi is not

The charter is explicit about its non-goals:

- **Not a rendering engine.** Phase 1 is interop with an existing renderer (Dioxus today).
  Rebuilding one buys the syntax and compiler layer nothing.
- **Not a tensor runtime.** ML inference is a declared capability backed by Candle.
- **Not a post-quantum cryptography project.** Named as a future thread and out of scope.
- **Not a web-framework target.** The compiled artifact is WASM, and native for desktop.
  Astro is one thin, optional distribution surface among several.
